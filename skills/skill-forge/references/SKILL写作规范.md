# SKILL写作规范
什么时候读我：写骨架时，或审别人的SKILL.md时。

## 一、目录
```
<name>/
  SKILL.md          必须。frontmatter + 正文，五百行内
  references/       按需读的知识，每文件开头一句"什么时候读我"，超300行加目录
  templates/        输出骨架
  scripts/          确定性计算或格式化，模型不该每次重写的东西
  evals/evals.json  种子问题与assertion
```

## 二、frontmatter
```
name: 小写连字符，与目录同名
description: >-
  一句身份 + 能做什么(具体到动作和产出) + 何时用(用户真会说的话)。
  触发词:口语/术语/变体，用斜杠分隔。
  英文触发:同上。
```
要点：
1. 描述是唯一的触发机制，"何时用"全写这里，正文里写没用。
2. 模型倾向于少触发，所以描述要推一把：把相邻场景也写进去，写"即使用户没说X也要用"。
3. 触发词按用户说话方式分层：老板话(卖不动/起不了量)、行话(鸿沟/滩头)、英文。
4. 描述别超过一屏，但宁长勿短。

## 三、正文骨架(固定顺序)
1. **身份与信条**：一句话说这个skill信什么。信条决定取舍，比流程重要。
2. **何时用**：三到五条场景，最后一条"用户提到任何触发词"。
3. **固定流程**：三到五步，每步写输入、判据、输出。有分支的写判据不写分支树。
4. **硬规则**：五到八条，每条带为什么。违反任一条要主动指出。
5. **常见误用**：四到六条反例。反例比正例管用，因为模型默认会犯的就是这些。
6. **输出规范**：格式、文件类型、存放路径、版本号、语言。
7. **参考索引**：每个参考文件一句"什么时候读"。

## 四、写作风格
1. 祈使句。"先算参与率再选算法"，不写"建议可以考虑"。
2. 解释为什么。模型有理论心智，懂了原因能举一反三。全大写的MUST是黄旗。
3. 通用而不窄。别把三个测试例子的细节写成规则，那是过拟合。
4. 例子用输入输出对。
5. 数字和阈值给经验值并标"经验值"，让模型知道可以按情境调。

## 五、分层加载
1. 描述永远在上下文(约百词)。
2. SKILL.md触发后进上下文(五百行内)。
3. references按需读，scripts可以不读直接跑。
主文件接近五百行就加一层目录并写清"接下来去哪读"。

## 六、业务锚
1. 写明用户是谁、站哪一方立场。
2. 分析落到钱上。
3. 输出语言、文件格式、存放路径、版本号规则写死。
4. 涉及具体公司的口径放本地文件，不进公开仓库。
