# 进料转skill
什么时候读我：手里有一本书、一份会议纪要、一段聊天记录或一个开源skill，要变成skill的时候。

## 通用原则
skill要的不是资料，是判断。任何进料都按同一套问题榨：
1. 这套东西**在什么情况下用、什么情况下不用**。
2. 它的**固定步骤**是什么，每步的判据是什么。
3. 它认为的**典型错误**是什么。
4. 它的**输出长什么样**(表、清单、陈述句式)。
榨不出这四样的进料，做不成skill，只能做参考资料。

## 一、一本书
1. 先列全书框架清单：每个框架一行(名字/解决什么/输入/输出)。
2. 挑出"有判据"的框架进流程，"只有概念"的进参考库。
3. 书里的案例换成目标用户的行业案例，原案例最多留一个当对照。
4. 书的章节顺序不等于流程顺序。按用户做事的顺序重排。
5. 版权：只固化方法论和自己的表述，不整段搬原文。

## 二、一份会议纪要
1. 先分清三种话：决策(定了什么)、判断(为什么这么定)、口径(以后按什么算)。
2. 决策和口径进硬规则，判断进"为什么"。
3. 一次会议通常只够写一条硬规则或一个流程步骤，合并到已有skill比新建更常见。
4. 说话人是老板的，原话尽量保留一句，作为信条。
5. 纪要里的数字标"当时值"，不要写死成阈值。

## 三、一段聊天记录
1. 找用户纠正过你的地方，每一处纠正都是一条硬规则。
2. 找用户反复问的问题，那是触发词。
3. 找最后被采纳的那版输出，那是输出模板。
4. 中途被否掉的方案写进常见误用。

## 进料后的自检
1. 能不能用一句话说这个skill"给谁、解决什么、和裸模型比强在哪"。
2. 硬规则有没有至少五条，每条带为什么。
3. 常见误用有没有至少四条。
4. 主文件是否在五百行内。
